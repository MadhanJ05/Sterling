# Fixtures

Every fixture and why it behaves the way it does. `expectations.json` is the machine-readable
version and was **written by hand before the checker was run against any of it**. If the checker
ever disagrees with a line there, the checker is wrong until the line is argued down on its merits.

## The job

`source-batch-1.json` — 12 products, IDs 1001–1012, supplied in **shuffled** order. The supplier
must return every product exactly once, keep each price, and sort by product ID ascending.

The stored source order matters: `1007, 1002, 1011, 1004, 1001, 1009, 1003, 1012, 1006, 1008,
1010, 1005`. Rule 2 scans the source in that order, so which of two simultaneous problems gets
reported is determined by it. Two fixtures below exist specifically to pin that down.

## Expected outcomes

| Fixture | Verdict | Rule | Why |
|---|---|---|---|
| `output-correct.json` | PASS | — | 12 rows, every ID once, prices unchanged, strictly ascending. |
| `output-missing-row.json` | FAIL | 1 | Product 1006 dropped → 11 rows. Row count is checked first, so this reports as a count failure, not a missing-ID failure. |
| `output-missing-source-id.json` | FAIL | 2 (MISSING) | 1002 replaced by a second copy of 1010. Count is still 12 and no ID is foreign. The source scan reaches 1002 (index 1) before 1010 (index 10). |
| `output-duplicate-id.json` | FAIL | 2 (DUPLICATE) | 1005 replaced by a second copy of 1007. The stored source order begins with 1007, so the duplicate is found before the missing 1005. |
| `output-unknown-id.json` | FAIL | 2 (UNKNOWN) | 1003 replaced with invented product 9999 at 111.11. The unknown-ID check runs before missing/duplicate, so 9999 is reported, at delivery row 11. |
| `output-wrong-price.json` | FAIL | 3 | 1009 delivered at 3490.00 against an approved 3499.00. |
| `output-wrong-order.json` | FAIL | 4 | Contents completely correct; 1005 and 1006 swapped. **The most interesting fixture:** right in substance, wrong against an agreed term. |

Only the **first** violation in the frozen order (1, then 2, then 3, then 4) is reported, which is
why a delivery with several problems names only one rule.

## Template reuse

The same acceptance pack template, rebound to different batches:

| Fixture pair | Rows | Why |
|---|---|---|
| `source-batch-2.json` / `output-batch-2-correct.json` | 8 | IDs 2001–2008, unrelated prices. |
| `source-batch-3.json` / `output-batch-3-correct.json` | 20 | IDs 3001–3020, source stored **descending**, to confirm the checker never assumes a sorted source. |

Each rebinding produces a new source commitment and a new pack digest. Reuse is of the *template*;
every job still binds its own source and its own terms.

## The clause software cannot check

Not a data fixture. The pack variant carrying "Make the product descriptions persuasive" is
classified `JUDGEMENT`, reports `unsupportedClauseCount = 1` and `fullyAutomatic = false`, and
`AcceptanceEscrow.createJob` reverts with `UnsupportedClausesPresent(1)`.

There is no committed predicate for "persuasive": two competent reviewers can read the same bytes
and disagree, and no check in this pack can settle it. Marking it executable would be a lie about
what the software can do. The only route forward is an explicit scope revision producing pack
version 2, where the clause is still listed and visibly marked `EXCLUDED_BY_REVISION` with its
reason. It is never deleted, and a revision cannot alter a job that already exists.

## Import boundary

Each of these is rejected with a named code and an actionable message. A rejection here is a
**bounded input rejection**, never a finding about delivered work.

| Fixture | Code | Why |
|---|---|---|
| `bad-malformed.json` | `MALFORMED_JSON` | Trailing comma. |
| `bad-fractional-price.json` | `PRICE_NOT_INTEGER` | 12.99 is not an integer number of cents. Money is never rounded silently. |
| `bad-unknown-field.json` | `UNKNOWN_FIELD` | A `description` field. Version 1 cannot carry it, and dropping it silently would hide part of the delivery. |
| `bad-price-as-string.json` | `PRICE_NOT_NUMBER` | `"1299"` is a string. No coercion. |
| `bad-duplicate-key.json` | `DUPLICATE_KEY` | `priceCents` twice in one object; `JSON.parse` would silently keep the last. |
| `bad-oversized.json` | `TOO_MANY_ROWS` | 40 rows against the documented bound of 32. |
| `bad-unsafe-integer.json` | `PRICE_NOT_SAFE_INTEGER` | Above `2^53−1`; `JSON.parse` would lose precision. Representable on chain as `uint64`, not importable from JSON in version 1. |
| `bad-negative-id.json` | `ID_OUT_OF_RANGE` | `productId` is unsigned. |

## Golden encoding vectors

`golden-vectors.json` is generated by `scripts/gen-golden-vectors.py`, which implements the ABI
layout by hand from `docs/encoding.md` and Keccak-256 from the permutation spec. It imports neither
ethers nor solc, so agreement between Python, TypeScript and Solidity is genuine
cross-implementation agreement rather than one library checked against itself.

Values are stored as decimal **strings**, because several vectors exceed `2^53` and `JSON.parse`
would round them — the same discipline the import boundary enforces on real input.

Nine vectors: empty array; both field minimums; both field maximums; two arrays differing only in
order; repeated IDs; values straddling 2^31, 2^32−1, 2^53 and 2^63; the 32-row maximum; and the
demo source batch in its stored order.

Regenerate with `npm run vectors` (needs Python 3).
